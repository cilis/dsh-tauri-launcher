# 桌面启动器版本规划（v1.1 → v2.0）

> **这是什么**：桌面启动器（`launcher/`，Tauri 应用）的对外版本规划，回答「下几个版本做什么、
> 为什么、怎么算做完」。
>
> **基线**：v1.0.11（`package.json` / `Cargo.toml` / `tauri.conf.json` 三处同号）。
> **取代关系**：本文取代工作区 `docs/roadmap.md`（2026-08-20，v1.0.0 时代审查）。旧文档的 13 项
> 逐条状态见 §2.2——其中 2 项已在 v1.0.5–v1.0.10 期间部分落地，其余仍然有效并已重新排期。
>
> **维护规则**：版本发布后回来勾状态；新增需求先进 §6 backlog，不直接插进当期；
> 决策结论落 §7 决策记录，不再回改上面的需求描述。
> **不承诺日期**：本规划只定顺序与范围，不给日历承诺。

## 1. 产品定位与当前痛点

启动器是 DSH 的**桌面门户 + 进程守卫**：它做三件用户自己不愿做的事——把 DSH 装起来、把 DSH 跑起来、
DSH 挂了能收尾。当前形态已能覆盖主路径（检测/安装/启动/接管/托盘/自启/快捷键/快捷方式）。

但用户侧的**信息缺口**和**控制缺口**仍然明显：

| 痛点 | 现象 | 本期是否解决 |
| --- | --- | --- |
| 拿不到版本信息 | 报障时要用户去翻 `package.json`、`npm ls -g`、命令行敲 `node -v`；「关于」入口不存在 | ✅ v1.1 |
| 不知道有没有新版 | 得自己去 GitHub Releases 翻；DSH 本体与启动器两条更新线都要各自查 | ✅ v1.1（只提示） |
| 收不干净界面 | 想只留托盘在后台，得挨个关窗口；关掉主窗后设置窗可能还开着 | ✅ v1.1 |
| 只留托盘不退出 | 缺少「把界面收干净但别退出应用」的一键入口 | ✅ v1.1 |
| 出问题没有历史证据 | 日志只有 256 行内存环形缓冲，重启即失 | v1.2 |
| DSH 崩了没人管 | 运行中崩溃无任何恢复机制 | v1.3 |

## 3. v1.1 —— 标题栏信息架构重建（本期）

### 3.1 需求与目标形态

用户已明确：新增「关于」菜单（含 关于 Launcher / 检查更新）与「窗口」菜单（含 关闭窗口）；
**「退出」保持原样留在「文件」菜单下**（2026-09-18 决定：不做迁移，见 §7）。

**菜单结构 before → after**

```
现在                                    目标
文件 ▾            帮助 ▾                文件 ▾        窗口 ▾       关于 ▾            帮助 ▾
├ 设置            ├ DSH官网             ├ 设置        └ 关闭窗口   ├ 关于 Launcher   ├ DSH官网
├ 重新加载页面     └ 文档                ├ 重新加载页面              └ 检查更新        └ 文档
├ 在浏览器中打开                        ├ 在浏览器中打开
├ ──────────                            ├ ──────────
└ 退出 ⚠                                └ 退出 ⚠        ← 不变（不迁移、不改名）
```

菜单顺序建议 `文件 · 窗口 · 关于 · 帮助`（功能菜单在前、帮助在后）。

> 注：本期「窗口」菜单只有一个条目是有意为之——它是后续窗口类操作（最小化到托盘、
> 窗口置顶、窗口尺寸记忆等）的归置位，新需求不再往「文件」里塞。

### 3.2 工作项

#### W1 · 关于 Launcher 弹窗 ✅ 复用度最高

- **价值**：报障时用户能自助提供三个版本号，省掉一轮「你装的哪个版本」的往返。
- **内容**：启动器版本 / DSH 版本 / Node 版本，三项各自容错（未安装 → 「未安装」，探测不到 → 「未知」）。
- **落点**：
  - Rust：新增命令 `get_versions()`（建议置于新文件 `src/info.rs`，与 `dsh.rs` 的「与 tauri 解耦」风格一致）
    - 启动器：`app.package_info().version`（`tray.rs` 已在用）
    - DSH：`dsh::check().version`（**已有，直接复用**）
    - Node：`dsh::node_exe()` + `--version`（约 10 行；`DSH_LAUNCHER_NODE` 覆盖已内置，测试可注入）
  - 前端：`index.html` 加 `#about-modal`（遮罩 + 面板）、`styles.css` 加样式、`main.js` 加 `setupAbout()`
  - ACL：`permissions/launcher.toml` 的 `commands.allow` 追加 `get_versions`
- **形态决策**：**页内 overlay，不新增 webview**（2026-09-18 定为 D7）。理由：任何新 webview 都必须遵守「启动早期预建」
  约束（iframe 加载跨源 DSH 后同步 build 会死锁），成本与风险都远高于一个 overlay。
- **验收**：
  - [x] 三个版本号与 `node -v`、托盘「版本 vX」、实际安装版本逐一对得上
  - [x] DSH 未安装时显示「未安装」，不报错、不阻塞弹窗
  - [x] Esc、点击遮罩、点击关闭按钮三种方式都能关闭
- **工作量**：S–M｜**风险**：低（Node 探测失败只影响一行显示）
- **实现注记（2026-09-30 合并，main `e277a87`）**：命令落在新文件 `src/info.rs`；前端 overlay 的 id
  是 `#about-overlay`（非本项草案里的 `#about-modal`）。三项容错由 Rust 侧返回 `Option` 实现，
  前端分别渲染「未安装」/「未知」。

#### W2 · 检查更新（v1.1 只提示 + 给全出路 = A+ 档） ✅

- **价值**：把「有没有新版本」从「去 GitHub 翻」变成一次点击。
- **检查两项（主检）**（2026-09-18 定，见 §7.1 D6）：
  1. **启动器 + 插件（合并为一项）**：运行中 exe 版本 vs npm `@lenorin/dsh-tauri-launcher` 最新版。
     两者**同号**——`build.ps1 -Bump` 同步三处版本号（`package.json` / `Cargo.toml` / `tauri.conf.json`），
     `ci.yml` 卡一致性，且 **npm 包自带 exe**；拆成两项等于把同一个数字展示两遍。
  2. **DSH 本体**：本机安装版本 vs npm `@deepseek-ai/dsh` 最新版。**独立版本号**（0.1.x），
     与启动器无关，不查就无从知道 DSH 有新版。

> **「漂移」的正确位置**：只有当用户跑的 exe **不是** npm 包里那份（自己从 GitHub Release 下载到
> 桌面/别处）时才可能不一致；走推荐路径（`dsh plugin add`，包内自带 exe）永远同步。故它**不占检测项**，
> 仅在实测到不一致时多显示一行附注——两个版本号本来就在手上，零额外探测成本。
> v1.0.10 的「自动发现运行中实例」处理的正是这种多副本场景。
- **落点**：新增命令 `check_updates()`，复用现有 `dsh::run_capture()` 调 `npm view <pkg> version`
  （复用既有工具链，**不新增 HTTP 依赖**）；exe 版本取 `app.package_info().version`，
  插件版本读已安装包的 `package.json`（本地文件读，不联网）。
- **硬约束**：CSP 为 `default-src 'self'`，**页面无法直连 npm registry** —— 必须由 Rust 侧发起。
- **体验要求**：加载态 + 超时（建议 8 秒）+ 失败给明确原因（离线 / npm 缺失 / 超时），不阻塞标题栏。
- **提示内容（A+ 档，2026-09-18 定，见 §7.1 D5）**：光说「有新版本」不够——必须一次给全**出路三件套**：
  1. **当前正在运行的 exe 完整路径**（多副本场景下不能显示包内副本路径，否则用户会替换错文件）
  2. 「打开下载页」按钮（GitHub Release）
  3. 「复制升级命令」按钮（插件侧命令直接进剪贴板）
  目标是用户不必自己拼「该升哪条路径、文件在哪、敲什么命令」。
- **v1.1 不做**：自动下载与安装（→ v1.2，见 §11.2）。
- **验收**：
  - [x] 断网时给出「检查失败：<原因>」，而不是一直转圈（超时阈值定为 **8 秒**，非草案的 3 秒：
    本机实测单次 `npm view` 约 3.7 秒，3 秒会把正常查询也误判成超时）
  - [x] 有新版本时展示「新版本 x.y.z」+ 出路三件套；没有时明确说「已是最新」
  - [x] 显示的 exe 路径 = **用户此刻真正在跑的那份**（取 `current_exe()`）
  - [x] 启动器与插件合并为一项（同号，不重复展示）；漂移仅在真不一致时多一行
- **工作量**：M｜**风险**：中（网络与 npm 可用性；靠超时 + 明确文案兜底）
- **实现注记（2026-09-30 合并，main `e277a87`）**：两项并行查询（`tokio::join!`），超时 8 秒；
  升级命令的 profile 名从已装插件路径推断（回退 `web`）。**未实测项**：「有新版本时的出路三件套」
  ——本地插件与 npm 上同为 1.0.11，检查走的是「已是最新」分支，该路径随下次发版自然覆盖；
  断网文案亦未实测（实现为 8 秒超时 + npm 失败原因透传）。

#### W4 · 关闭窗口（关闭所有窗口，不退出应用） ✅

- **价值**：一键把界面收干净，保留托盘与 Harness 后台运行。
- **落点**：新增命令 `hide_all_windows()`（`windows.rs`），对 `WINDOW_MAIN` / `WINDOW_SETTINGS` 执行 `hide()`。
- **🔴 红线**：**绝不能复用 `close_visible_windows()`** —— 它执行的是 `destroy()`（退出流程专用）。
  destroy 之后没有重建路径，托盘「打开」会失效，等于把应用变成僵尸。本项必须用 `hide()`。
- **重开路径**：托盘 `MENU_SHOW` 已是 `show + unminimize + set_focus`，**无需改动**（已具备）。
- **命名**：定为**「关闭窗口」**（2026-09-18 决定）——与「文件 → 退出」形成「关窗 vs 退出」的
  明确对照，避免两个「退出」并排造成误点。
- **验收**：
  - [x] 点击后主窗与设置窗同时消失，托盘图标仍在
  - [x] Harness 子进程不受影响（Web GUI 仍可访问）
  - [x] 托盘「打开 DeepSeek Harness」能恢复主窗口，且 iframe 内会话仍在（不是重新加载）
- **工作量**：S
- **实现注记（2026-09-23 开工，2026-09-29 合并进 main `d259919`）**：`hide_all_windows()` 已落地
  （`windows.rs`，只用 `hide()`，红线已写入函数文档），ACL 已授权（审计 15/15 零差异）；
  **三条验收已人工冒烟通过（2026-09-29）。**

#### W5 · 托盘左键单击打开 / 聚焦主窗口 ✅

- **价值**：左键单击托盘图标直接打开或聚焦主窗口，不用先点菜单。
- **落点**：`tray.rs` 的 `build_tray()` 加 `.on_tray_icon_event()` 回调。
- **实现**（与草案的差异见注记）：
  - `TrayIconEvent::Click`（左键、抬起）→ 打开或聚焦主窗口
  - 菜单改**右键**弹出：左键让给了「打开 / 聚焦」
- **工作量**：S｜**风险**：低（只加事件处理，不动现有逻辑）
- **实现注记（2026-10-03 合并，main `05f6dda`）**：**取消了草案里的双击**——用户决定
  （2026-10-03）：左键单击已经把窗口打开了，双击只会让同一次操作触发两遍（Windows 上
  双击必先落两次单击事件，两个分支都处理等于重复调用）。因此 `DoubleClick` 分支没有写。
  事件只认**抬起**（`MouseButtonState::Up`，按下与抬起各来一次），与菜单
  「打开 DeepSeek Harness」共用 `open_or_focus_main`：已可见且未最小化只聚焦、
  最小化则还原、「关闭窗口」隐藏后重新显示。

#### W6 · 链接跳转：DSH 外部链接在默认浏览器打开 ✅

- **问题**：点击 DSH 里的外部链接（`target="_blank"` / `window.open`）**没有反应**——WebView2 默认阻止新窗口请求（无 handler）。
- **根因**：主窗口通过 `tauri.conf.json` 创建，没有挂 `on_new_window` handler。
- **方案**：把主窗口创建从 `tauri.conf.json` 移到 Rust 代码，加 `on_new_window` handler 转发到系统浏览器。
- **落点**：
  - `lib.rs`：在 `setup()` 中用 `WebviewWindowBuilder` 创建主窗口，加 `on_new_window`
  - `tauri.conf.json`：移除 `windows` 数组中的 `main` 配置
  - `windows.rs`：`open_with_system_browser` 改为 `pub(crate)`
- **风险**：移动窗口创建可能影响启动时序（图标/托盘/预建窗口的顺序），需仔细测试。
- **工作量**：M｜**风险**：中（涉及窗口创建流程）
- **实现注记（2026-10-03 合并，main `151ae81`）**：落点与草案有一处不同——**没有移除
  `windows` 数组**，而是给 main 加 `"create": false`，再用 `WebviewWindowBuilder::from_config`
  读回同一份配置建窗口（窗口属性仍留在 `tauri.conf.json` 这一处，不必搬进 Rust）。
  `setup()` 顺序定为 `prebuild_aux_windows` → `build_main_window` → 图标 / 托盘。新窗口请求
  一律 `Deny`、只放行 http/https。`lib.rs` 的 `main_window_is_built_manually` 钉住
  `create: false` 那一行——删掉它会静默退回「点了没反应」。

#### W9 · 一键发版脚本 ⭐ 建议首先做 ✅

- **价值**：v1.1.0→v1.1.2 一天内连发三版，每次都走同一串固定动作——校验 CHANGELOG 小节 →

#### W19 · 剪贴板放行（2026-10-21，随 v1.1.5 发布）✅

- **现象**：外壳窗口里文字能选中，但 Ctrl+C 与 DSH 的复制按钮都没有反应，按钮也不出现「已复制」。
- **根因**：DSH 在跨源 iframe（3081 → 3080）里，`clipboard-write` 的默认白名单只覆盖 `self`，
  iframe 未声明 `allow` 即被权限策略拒绝；且 tauri 默认 `clipboard=false`，wry 不注册
  WebView2 的 `PermissionRequested` 处理器。
- **修法**：iframe 加 `allow="clipboard-read; clipboard-write"`；主窗口 builder 加
  `.enable_clipboard_access()`。原理与注意事项见 architecture.md「剪贴板（2026-10-21）」。

## 10. Vue3 + daisyUI 架构评估（2026-09-18）

> 本节回答「要不要把启动器前端升级成 Vue3 + daisyUI」。结论是**不要现在做**，
> 但保留触发条件。

### 10.1 需求 vs 方案

用户提出的真实需求是「更好的性能、可读性、交互效果、可维护性」，提出的方案是 Vue3 + daisyUI。
两者不是一回事——方案可能不解决问题。

### 10.2 逐项评估

| 维度 | 现状 | Vue3 + daisyUI | 差距 |
|------|------|----------------|------|
| **性能** | 无框架开销，启动快 | Vue 运行时 + daisyUI CSS → 启动器变大变慢 | ❌ **负优化** |
| **可读性** | ~800 行，组织成函数，有注释 | Vue SFC + 组件化 | ✅ 提升，但当前不难读 |
| **交互效果** | 手写 CSS，自定义标题栏匹配 DSH | daisyUI 预制组件 | ⚠️ 部分提升，但标题栏不匹配 |
| **可维护性** | 零依赖，无构建 | npm 依赖 + 构建步骤 | ⚠️ 有得有失 |

### 10.3 成本估算

重写需要：加 Node/npm 构建步骤 → 加 Vue3 + daisyUI + Tailwind 依赖 → 重写 ~800 行 UI →
调整 CSP → 调整 Tauri 配置 → 测试所有现有功能（托盘、窗口、主题、会话导航）。

**估计成本**：3–5 天 + 回归测试。**收益**：不确定。

### 10.4 为什么不做

1. **启动器的 UI 是"外壳"，不是"应用"**。真正的应用是 DSH Web（iframe 里）。
   给这个壳用 Vue3 就像用推土机种花。
2. **性能是负优化**。Vue3 + daisyUI 让启动器变大变慢，对"打开后用户进 DSH"的场景无意义。
3. **当前代码已经足够好**。~800 行，组织成函数，有注释，有规范。问题不是"代码烂"，是"功能缺"。
4. **风险高**。重写意味着所有现有功能要重新实现和测试。
5. **daisyUI 不匹配**。启动器的标题栏是自定义的（匹配 DSH 的 `--dsw-*` token），
   daisyUI 的预制组件反而会增加不一致性。

### 10.5 更务实的改进方案（推荐）

| 方案 | 成本 | 收益 | 建议 |
|------|------|------|------|
| **A. TypeScript** | 低（加 `tsconfig.json`） | 类型安全、IDE 支持、减少运行时错误 | ✅ 推荐 |
| **B. 模块化拆分** | 低（拆 `main.js` 成多个模块） | 更好的可读性、更容易定位问题 | ✅ 推荐 |
| **C. CSS 变量化** | 低（提取硬编码颜色值） | 更容易维护主题 | ✅ 推荐 |
| **D. 等 UI 复杂度增长再框架化** | 零 | 避免过度工程 | ✅ 推荐 |

### 10.6 触发条件（何时重新评估）

如果未来出现以下情况，再考虑 Vue3 + daisyUI：

- 启动器 UI 复杂度显著增长（多个设置页、通知中心、状态面板）
- 需要频繁添加新的 UI 组件
- 团队扩大，需要组件化协作

当前启动器的 UI 只是一个启动画面 + 标题栏 + 菜单，远未达到需要框架化的复杂度。

**体检发现（比「要不要上框架」更值得修的三件事）**

1. **色板重复**：`settings.css` / `exiting.css` 与 `styles.css` 有 **9 个重复色值**
   （`#15304b` / `#1c2644` / `#0b0f17` / `#e5eaf2` 各出现 3 次，另 5 个各 2 次）——改一次品牌色要动三个文件。
2. **变量化已有骨架**：10 个 `--tb-*` 由 `main.js` 运行时 `setProperty` 注入（跟随 DSH 主题），
   `styles.css` 只消费不定义——**缺的不是框架，是把另外两个页面接进同一套变量**。
3. **一行造成的可读性假象**：`index.html` 那行 15,171 字符的 SVG，让 109 行的文件看起来像 20KB 怪物。

**硬约束（决定了框架方案的形态）**

- **无构建步骤**：`ui/` 三文件经 `include_str!` 直接进 Rust 二进制（`shell_server.rs:29-31`），
  `settings` / `exiting` 走 tauri 资产协议 → Vue SFC / TypeScript **必须先引入 Vite 流水线**
  （改 CI + 产物入库或构建期生成）。
- **外壳页有自己的 CSP**：`script-src 'self'; style-src 'self'`（`shell_server.rs:26`）→
  **CDN 方式不可用**；且无 `'unsafe-inline'`，内联 `style="…"` 属性会被拦——现有三个 HTML 的
  内联样式数**都是 0**（审计结果），与该 CSP 一致，新增 UI 必须沿用外置样式类的写法。

**结论（复评后不变，但理由更硬）**

| 诉求 | Vue3 + daisyUI 能否改善 | 依据 |
| --- | --- | --- |
| 性能 | ❌ 反向 | 外壳自身只有 632 行 JS，重量全在 iframe 内的 DSH；框架只增加解析与响应式开销 |
| 可读性 | ❌ 不对症 | 痛点是 id 字符串查找、三份重复色板、一行 15K 字符——框架一个都不解决 |
| 交互效果 | ⚠️ 有限 | daisyUI 的视觉体系与「自绘标题栏 + 跟随 DSH 主题 token」冲突；真正缺的是过渡动画 / 键盘导航 / focus 可见性，CSS 即可 |
| 可维护性 | ⚠️ 需先付构建成本 | 换来 Vue 的最强形态，代价是新构建流水线 + 产物管理 |

**替代改进（「零构建现代化」，全部不引入构建步骤）**

| # | 动作 | 成本 | 收益 |
| --- | --- | --- | --- |
| **A** | 抽 `vars.css` 共享色板（shell server 加一行 `include_str!`，另两页 `<link>` 引入） | 小 | 消除 9 处重复；品牌色一处改 |
| **B** | 品牌 SVG 移出为 `logo.svg` | 小 | `index.html` 去掉 15K 字符长行 |
| **C** | `main.js` 拆 ES Modules（`<script type="module">` 原生支持、零构建） | 中 | 532 行 → 每模块 100~200 行 |
| **D** | 引 Vue3 + daisyUI | 大 | 不确定（见上表） |

**已定（D9，2026-09-18）**：**不做** Vue3 + daisyUI；A（`vars.css` 共享色板）与 B（SVG 拆行）
作为 **W7 / W8 编入 v1.1**；**C（`main.js` 拆 ES Modules）单独排到 v1.2**——它与 W3 同改
`main.js`，并行会让 diff 无法审阅。

**重新评估的触发条件（更新）**：UI 页面数 > 3、单个 JS > 1,000 行、或出现需要框架级状态同步的场景
（实时日志看板、多窗口状态联动）。

## 11. 升级机制演进路线（2026-09-18）

> 回答用户问的：「检测到新版本提示用户退出，用户点击确认退出自动升级呢？用命令的方式？
> 后续再改成用安装包安装的方式升级，可有路线？」

### 11.1 核心洞察：把 Windows 文件锁从阻碍变成路径

exe 正在运行时无法被替换（Windows 文件锁）。**「退出后升级」把锁变成路径**：
exe 退出 → 旧文件自然可删 → 新 exe 已在 npm 包缓存里 → 只需一次移动。

这是「自动升级」最省事的路径——不用走 tauri-plugin-updater 的签名体系，
也不用自己实现差量更新。

### 11.2 命令方式的升级链路（已验证可行）

**前提（2026-09-18 核实）**：`dsh plugin` 底层是 **pnpm 薄转发**（`lib/plugin-Ddi42qoW.js`
的 `runPlugin` 把参数原样传给 `pnpm`），所以 `pnpm update` / `pnpm upgrade` 天然可用。

#### 命令链路

```
用户点「退出并升级」
  ↓
关闭启动器（解锁 exe 文件锁）
  ↓
检测 exe 是否在运行 → 在则终止（taskkill /PID /F 或优雅退出）
  ↓
pnpm update @lenorin/dsh-tauri-launcher --profile web
  （拉最新包，内含新 exe + 新插件代码）
  ↓
把新 exe 从 ~/.dsh/profiles/web/node_modules/.../launcher/bin/
  复制到当前 exe 所在目录（或用户选的位置）
  ↓
启动新 exe
```

#### 关键实现细节

| 问题 | 解法 |
|------|------|
| **exe 文件锁** | 用户确认退出 → 先 `hide` 所有窗口 → 执行升级 → 重启 |
| **exe 在 Program Files 下没写权限** | 检测目录可写性；不可写时提示用户用管理员身份，或改用用户目录安装（`%LOCALAPPDATA%\Programs\`） |
| **pnpm update 需要网络** | 离线时提示「请联网后重试」；失败时回滚（旧 exe 还在原位） |
| **升级后旧 exe 去哪** | 重命名为 `dsh-launcher.exe.old`，下次启动时删除；或放 `recycle bin` |
| **如何知道 exe 当前位置** | 进程路径探测（`Get-Process dsh-launcher` 取 `Path`） |

#### 与现有代码的复用

| 现有能力 | 复用方式 |
|---------|---------|
| `dsh.rs::check()` | 检测当前安装版本 |
| `run_capture()` | 执行 `pnpm update` |
| `install_dsh()` 的日志透传 | 升级进度展示 |
| `process.rs::kill_processes_on_port()` | 检测并终止运行中的 exe |
| `Get-Process` + `Path` | 定位当前 exe 位置 |

### 11.3 安装包方式（NSIS）的演进路线

「安装包安装」不是替代命令方式，而是**并行的另一条分发线**。适用场景：

| 场景 | 命令方式（pnpm） | 安装包方式（NSIS） |
|------|----------------|------------------|
| **已有 DSH + 插件** | ✅ 最省事 | 不需要 |
| **全新用户** | 要先装 Node + pnpm + DSH | ✅ 一步到位 |
| **企业内网分发** | 依赖 npm registry | ✅ 离线可用 |
| **版本回滚** | `pnpm update` 到指定版本 | 装旧版安装包 |

#### 演进路线（三步走）

```
第一步（v1.2）：命令方式先行
  └─ pnpm update + exe 文件替换
  └─ 解决「已有用户」的升级痛点（最常见）

第二步（v1.3）：安装包并行
  └─ tauri build 产出 NSIS 安装包（tauri.conf.json 已配 bundle.targets）
  └─ CI 自动上传 GitHub Release
  └─ 安装包内嵌「检查更新」逻辑（启动时或设置里手动）

第三步（远期）：统一升级入口
  └─ 设置面板显示「当前版本 / 最新版本」
  └─ 自动检测用户是从哪条路径安装的（npm / 安装包）
  └─ 分别走对应的升级逻辑
```

#### NSIS 安装包的技术要点

| 要点 | 说明 |
|------|------|
| **产出** | `tauri build` 自动产出 `.exe` 安装包（NSIS） |
| **签名** | 需要代码签名证书（否则 Windows SmartScreen 会警告） |
| **升级检测** | NSIS 安装包可检查已安装版本，提示升级 |
| **静默升级** | `dsh-launcher-setup.exe /S` 静默安装（企业部署用） |
| **卸载** | NSIS 自动注册到「控制面板 → 程序和功能」 |

### 11.4 与「检查更新」的联动

「检查更新」和「自动升级」是两个独立功能，但应该**共用检测结果**：

```
检查更新（只提示）
  ├─ 启动器 + 插件：当前 v1.0.11 → 最新 v1.0.12（有新版本；**同号，合并为一项**）
  ├─ DSH 本体：当前 0.1.5 → 最新 0.1.6（有新版本；**独立版本号**）
  └─ 漂移：一致 → **不显示**；只有实测不一致时才多一行附注

用户看到提示后，选择：
  ├─ 「仅提示」→ 记住，下次再说
  ├─ 「退出并升级」→ 走 11.2 的命令链路
  └─ 「去下载页」→ 打开 GitHub Release，手动下载（兜底）
```

> **v1.1 实现范围（2026-09-18 定，A+ 档）**：本期只做**提示层**——检测结果 + 当前 exe 路径 +
> 「去下载页」+「复制升级命令」；「退出并升级」这条动作链路留到 v1.2，届时直接复用同一份检测
> 结构，不再重复探测。

### 11.5 版本排期建议

| 版本 | 内容 | 理由 |
|------|------|------|
| **v1.1** | 检查更新（A+ 档：两项主检 + 出路三件套；漂移仅不一致时附注） | 先让用户「知道」有新版，且知道**下一步该做什么** |
| **v1.2** | 命令方式自动升级（pnpm update + exe 替换） | 解决「已有用户」的升级痛点 |
| **v1.3** | 安装包方式（NSIS） | 解决「新用户」的安装痛点 |
| **v1.4** | 统一升级入口（设置面板整合） | 两条路径合并，体验统一 |

### 11.6 风险与缓解

| 风险 | 缓解 |
|------|------|
| **pnpm update 失败**（网络/权限） | 检测失败原因，提示用户手动操作；旧 exe 不删，可回滚 |
| **exe 在 Program Files 下没写权限** | 检测目录可写性；提示用管理员身份，或改用用户目录安装 |
| **升级后新 exe 不兼容旧插件** | 检查更新时同时检查插件版本；不兼容时提示先升级插件 |
| **用户误点「退出并升级」** | 二次确认对话框；升级前备份旧 exe 为 `.old` |
| **NSIS 安装包没有签名** | 短期接受 SmartScreen 警告；长期考虑购买代码签名证书 |
